00 任務簡報

系統上線後的第一個陷阱，是把「CI 全綠、Production 有回應」誤讀成「沒有安全問題」。這套儀表板的信任模型建立在一個原則上：任何異常都該 fail closed。這份計畫的任務，就是驗證這條防線在真正被逼近邊界時是否還站得住——不是重新測一遍功能，是去找防線本身的縫。

啟動這份計畫的直接原因，是一次獨立程式碼複查已經在零基礎驗證、bootstrap 測試覆蓋率、分頁上限三處找到具體、可重現的缺口（見 §3）。這些不是猜測，是帶著檔案行號與重現步驟的真實發現。紅隊的工作從這裡往外擴：把這三個已知缺口正式排入測試矩陣，同時假設「如果找得到這三個，附近大概率還有沒被找到的」，系統性地把整個攻擊面掃過一輪。

本文件除保留原始測試規劃，也記錄實際改善證據。三項已知缺口已依 §10 完成 failing-test-first 修復及本機 deterministic 驗證，狀態為 VERIFIED；真實 PCC 與發布管線仍須由人工以 workflow_dispatch 做部署前確認。

01 授權範圍與交戰規則

範圍內

  • Repository 原始碼：scripts/、src/、tests/、config/。
  • GitHub Actions workflow 定義與其權限設計（.github/workflows/）。
  • 建置產出 dist/ 與發布資料 public/data/tenders.json 的內容完整性。
  • 本機與 CI 可重現的攻擊模擬（fixture、mock、`workflow_dispatch` 手動觸發）。

範圍外（明確排除）

  • PCC 官方網站與基礎設施——不對 web.pcc.gov.tw 進行任何形式的負載測試、爬蟲濫用或滲透測試；本系統對 PCC 而言只能是「行為良好的訪客」。
  • GitHub 平台本身——不測試 GitHub Pages／Actions 平台層的安全性，只測試我們如何使用它。
  • 對外部套件維護者、CDN 供應商（如 jsdelivr）發動任何實際攻擊——僅止於書面情境分析。
  • 任何會員生產資料遺失、Pages 停機、或消耗他人 CI 配額的破壞性操作。
交戰鐵律：先分析、後動手。任何會觸發真實 workflow_dispatch、真實對外請求或修改 Production 分支的測試，執行前需先取得系統負責人確認排程時段。詳見 §9。

03 已知缺口日誌

以下三項來自本次交付前的獨立程式碼複查，狀態全數 VERIFIED。本節保留原始缺陷描述，並補上實際修復與 regression test 證據，作為測試矩陣（§4）RT-001～003 的直接依據。

RT-001 · 確認零筆可能 fail-open

嚴重度 HIGH
位置 scripts/lib/tenderParser.ts:88
缺陷 html.includes("無符合條件資料") 是樸素子字串比對；把這段文字埋進 <script> 或 HTML 註解也會被判定為合法零筆。
影響 PCC 若結構漂移但頁面殘留該字串，系統會更新 fetchedAt 並正常發布，對外誤稱同步成功——這正是 fail-closed 設計原本要防的情況，卻被繞過。
建議方向 改驗證特定零筆 DOM 節點（如 pagebanner=0）等多重證據，不能只憑一段自由文字。
修復驗證 零筆須同時具備合法 td.tb_b2 內容節點、無標案資料列及 #pagebanner「共有 0 筆資料」。PAR-T-003b～003e 驗證真實零筆、script、註解及缺少 pagebanner 情境。

RT-002 · Bootstrap 核心流程沒有測試與 coverage

嚴重度 HIGH
位置 scripts/fetch-tenders.ts:32；coverage 範圍見 vitest.config.ts:20
缺陷 vitest.config.ts 的 coverage include 只涵蓋 scripts/lib/**/*.ts，不含 fetch-tenders.ts 本身；首次回填判斷、fallback、最終合併與 metadata 組裝完全沒有測試斷言。
影響 這正是先前「前一版存在但零筆」導致回填永遠不觸發那次事故沒被測試攔下來的根因——關鍵路徑本身是測試盲區。
建議方向 至少覆蓋：previousDataset === null 觸發回填、前一版零筆觸發回填、回填失敗改例行查詢、fallback 也失敗時不寫入 JSON、bootstrap 最終合併與 metadata 正確性。
修復驗證 orchestration 已抽為可注入的 runFetchPipeline()，CLI 只依回傳結果設定 exit code。FETCH-T-001～007 覆蓋 bootstrap 判斷、fallback、雙重失敗不寫檔、metadata、原子寫入及安全 CLI 入口；coverage 已納入 scripts/fetch-tenders.ts。

RT-003 · 達到最大頁數時靜默截斷

嚴重度 MEDIUM
位置 scripts/lib/pccPagination.ts:59
缺陷 迴圈跑滿 maxPages 後直接 return，即使最後一頁仍有「下一頁」連結；已用 maxPages=2 重現：第二頁仍有下一頁，函式仍視為成功回傳兩頁。
影響 tests/unit/pcc-pagination.test.ts:60 甚至把這個行為斷言為正確結果——測試在保護一個錯誤假設。首次回填若真的超過 400 頁，會發布一份被截斷的 40,000 筆資料集，而不是 fail closed。
建議方向 達到 maxPages 上限時，若仍偵測到「下一頁」連結存在，應視為異常並 fail closed，而非靜默視為完整資料集。
修復驗證 fetchAllPccPages() 在最後允許頁仍存在下一頁時拋錯；PAG-T-005／007／011 與 FETCH-T-008 驗證例行、剛好抓完、bootstrap 上限及安全 fallback。

05 方法論與時程

五個階段，循序但可重疊；每階段結束才進入下一階段的重測子集。

PHASE 0 · 偵察

攻擊面確認

覆核 §2 攻擊面地圖是否完整；盤點所有信任邊界與資料流入口，補齊本計畫尚未列出的節點。

PHASE 1 · 靜態分析

程式碼與設定複查

逐一驗證 RT-001／002／003；對 scripts/、.github/workflows/ 做手動 code review，尋找同類型的樸素字串比對、未覆蓋分支、隱含信任假設。

PHASE 2 · 動態與對抗性測試

fixture 注入與邊界模擬

執行 RT-004～009；以 mock HTTP 伺服器與 crafted fixture 重現攻擊情境，全程不對真實 PCC 或 GitHub 平台發出流量。

PHASE 3 · 供應鏈稽核

依賴與 Action 完整性

執行 RT-004／005／010；核對所有 Action SHA、CDN SRI、npm 依賴的實際來源與雜湊。

PHASE 4 · 報告與驗收

發現彙整與退出判定

依 §6 嚴重度分級整理所有發現，對照 §7 退出準則判定是否可結案；未修復項目需系統負責人書面風險承擔簽核。

09 交戰紀律

  1. 先分析、後動手——任何會觸發真實網路請求或真實 workflow_dispatch 的測試，執行前必須取得系統負責人確認排程時段。
  2. 不對 PCC 官方基礎設施、GitHub 平台本身、或任何第三方服務發動實際攻擊；供應鏈情境一律以書面分析與隔離分支模擬進行。
  3. 所有測試優先使用 fixture／mock，不使用真實個資或真實憑證；不主動蒐集、留存超出驗證目的所需的任何資料。
  4. 發現一律先私下回報系統負責人，經確認與修復後才可對外揭露；不進行未經授權的公開揭露。
  5. 本計畫本身不構成修復授權——修復程式碼需另行走專案既有的 TDD 與 npm run validate 全套流程，不得為求結案而放寬既有品質閘門。

10 改善規劃

三項已知缺口（§03）已依下列優先序完成。改善過程遵循專案既有慣例：SDD 先定義設計變更與介面影響，TDD 先寫失敗測試再實作、通過後才重構——比照 docs/pm/index.html STP §3「測試策略」與 docs/specs/001-pages-migration/test-plan.md「TDD 規則」的既有格式，不另創一套規範。本節保留原始規劃並補上實際執行證據。

執行優先序

  1. 1 RT-002 Bootstrap 核心流程補測試 —— 專案已真實發生過一次因此路徑無測試而上線的事故（見 ADR-002 附錄），修復成本低（只補測試，不動生產邏輯）、風險降幅最大，優先處理。
  2. 2 RT-001 確認零筆改多重證據驗證 —— 直接牴觸專案自訂的 fail-closed 原則，修復成本低，但需要先取得真實 PCC 零筆頁面 fixture 才能定義具體 DOM 錨點，不能用猜的。
  3. 3 RT-003 分頁上限改 fail closed —— 現有 1.7 倍安全緩衝（23,091／400 頁）使急迫性較低，但現有測試把錯誤行為斷言成正確結果，屬於需要清除的負資產。
執行結果：RT-002 的五個初始測試先因缺少可注入介面而 Red，RT-001 的三個惡意／不完整零筆案例先 Red，RT-003 的上限與 bootstrap fallback 案例先 Red；完成最小實作後，相關 FETCH-T-*、PAR-T-* 與 PAG-T-* 測試全數 Green。詳細 ID 與指令已同步至 test-plan.md、traceability.md。

RT-002 · Bootstrap 核心流程補測試

SDD 設計變更 scripts/fetch-tenders.ts 的 main() 目前直接呼叫真實 fetch／檔案系統，無法單元測試。比照 baseline.ts 既有的 loadPreviousPagesDataset(repository, fetchImpl = fetch) 可注入依賴慣例，把 orchestration 抽成可注入依賴的匯出函式（例如 runFetchPipeline(deps)），預設參數對應現有真實實作，CLI 進入點改為呼叫該函式並依回傳結果決定 exit code，而非直接 process.exit()。
介面影響 新增一個可測試的匯出函式；vitest.config.ts 的 coverage include 需把 scripts/fetch-tenders.ts 納入，不再限於 scripts/lib/**/*.ts。CLI 對外行為（exit code、寫入的 JSON 內容）不改變。

RT-001 · 確認零筆改多重證據驗證

前置條件 目前沒有真實 PCC 零筆頁面的具體 DOM 結構可參考——修復前必須先實際查詢一次 PCC 產生真正的零筆結果頁，蒐集去識別、不含 cookie／secret 的最小 fixture，確認可用的 DOM 錨點（例如特定 class／id 的容器元素），不能只憑猜測設計驗證邏輯。這點延續專案既有紀律：ADR-002 當初也是先用真實瀏覽器操作驗證西元年格式，才發現「不能用猜的」。
SDD 設計變更 parseTenderHtml() 的零筆判斷從「HTML 全文包含某段字串」改為「在特定內容區塊 DOM 節點內找到零筆標記，且沒有標案資料列，且（若前置條件蒐集到可用信號）分頁區塊也顯示零筆」——多重證據皆成立才視為確認零筆，任一證據缺席則視為結構漂移並拋錯。
介面影響 parseTenderHtml() 對外行為不變（回傳型別、正常零筆情境的結果一致），只收斂「什麼樣的輸入會被接受為合法零筆」的判斷範圍。

RT-003 · 分頁上限改 fail closed

SDD 設計變更 fetchAllPccPages() 迴圈結束時需要區分兩種情況：「最後一頁沒有下一頁連結（正常結束）」與「跑滿 maxPages 但最後一頁仍有下一頁連結（被截斷）」。後者應拋出明確錯誤（例如「分頁數超過安全上限，可能資料不完整」），而不是靜默回傳已擷取的頁面。
介面影響 fetchAllPccPages() 在正常情境（未達上限）行為不變；新增一種會拋錯的失敗情境。由於 fetchBootstrapOrFallback() 已有 try/catch 會在任何拋錯時退回例行 isNow 查詢，這個新錯誤會自動被既有 fallback 機制吸收，不需要額外新增呼叫端邏輯——但需要一則整合測試明確驗證這個銜接確實如預期運作，不能只假設。
