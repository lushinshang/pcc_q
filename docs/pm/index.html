Product Requirements Document

PRD — 產品需求文件

說明「為什麼做這個系統、給誰用、成功長什麼樣子」——工程規格細節不重複，一律連結到 SRS／SDD。

v1.0 狀態：草案（回溯性補齊） 最後更新 2026-07-25

§1 背景與問題陳述

政府電子採購網（PCC，web.pcc.gov.tw）是台灣政府標案公告的單一官方來源，但其網頁介面每次查詢僅能鎖定單一機關與短時間窗，且原始網站需要手動翻頁、無法依機關快速比較，也沒有可程式化訂閱的公開 API。對於需要每天掌握特定機關（如國防部）標案動態的使用者，人工瀏覽 PCC 網站查找、跨頁比對、判斷是否為新公告是重複且容易遺漏的工作。

本專案的前身是一個以 Google AI Studio 產生的原型（含 Express 後端、Gemini API、需要 API key），存在明確的安全與維運負擔（後端伺服器、API key 管理、生成式 AI 依賴皆非必要）。此次改造的產品目標是把它變成一個免維運、免密鑰、資料可驗證的公開儀表板。

§2 目標使用者

  • 主要使用者：需要每日掌握國防部（及未來可能擴充之其他中央／地方機關）標案公告的人員——例如採購承辦、投標廠商業務、政策研究者。
  • 次要使用者：對政府標案資料本身感興趣、想快速篩選特定機關／時間範圍標案的一般公眾。
  • 使用情境為「查詢與瀏覽」，不含投標、下單、聯絡機關等交易行為——本站明確不是交易平台。

§4 範圍與非範圍

範圍內

  • 不限機關逐頁擷取 PCC 標案公告（例行查詢當日；首次執行回填過去 30 天）。
  • 前端本地端篩選：機關（白名單，含所有下轄單位）、日期範圍（當日／一週／一個月）、案名／案號關鍵字、招標方式。
  • 30 天滾動資料視窗（自動剪枝超過 30 天的舊記錄）。
  • 資料來源、同步頻率、機關白名單的公開說明面板。
  • 自動化排程更新（平日每 3 小時）與人工觸發。

範圍外（明確排除）

  • 使用者帳號、登入、個人化訂閱或通知（email／推播）。
  • 標案投標、下單、聯絡窗口等交易行為。
  • 非公開資料或需登入才能查詢的 PCC 內容。
  • 生成式 AI 摘要／問答功能（前身原型曾用 Gemini，此版本刻意移除）。
  • 自訂網域、CDN、反向代理等額外基礎設施（除非另行授權）。
  • 行動 App、瀏覽器擴充套件。

§5 產品原則

  1. 零信任上游輸入：PCC HTML 一律視為不受信任來源，任何進入發布資料的內容都要經過 schema 驗證。
  2. Fail closed 優先：偵測到資料異常（結構漂移、同日新增驟減、拒絕比例過高）時停止發布，保留上一版，不讓錯誤資料上線。
  3. 免密鑰、免後端：不引入任何需要保管密鑰的元件；能用純靜態達成的功能不引入伺服器。
  4. 可驗證優於可承諾：任何「已完成」的宣稱都要有可重現的驗證證據，不接受「應該沒問題」。
  5. 公開資料，非官方整理：頁面明確標示本站非官方，內容以 PCC 公告為準。

§7 假設與依賴

  • PCC 網站持續以現有 HTML 結構與查詢參數對外開放，不需登入即可查詢任意機關。PCC 若改版介面會導致擷取失敗（設計上會 fail closed 並保留舊版）。
  • GitHub Pages／Actions 服務持續可用；未啟用 branch protection，權限控管依賴 workflow 內部設計而非平台強制。
  • 使用者以現代瀏覽器（支援 ES Module、<details> 原生互動）存取。

§8 已知限制

  • 無使用者流量／行為分析，§3 成功指標僅能以工程驗收數據代理。
  • GitHub Pages 無法由 repository 自訂完整 HTTP response headers（HSTS、X-Frame-Options、Permissions-Policy 等不在控制範圍內）。
  • 機關白名單為靜態列舉，新增機關需修改程式碼並重新部署。
  • 排程頻率固定為平日每 3 小時，非即時（分鐘級）更新。

§9 路線圖

  • Later 使用者可自訂追蹤機關清單（需重新評估零後端原則是否相容）。

3.2 使用者類別

見 PRD §2。系統不區分帳號或權限層級——所有訪客看到相同的公開資料與相同的篩選能力。

3.3 運作環境

  • 資料擷取端：GitHub Actions runner（ubuntu-latest），Node.js 24。
  • 發布端：GitHub Pages（純靜態，無伺服器端執行環境）。
  • 使用端：現代桌面／行動瀏覽器，支援 ES Module。

3.4 設計與實作限制

  • 不得引入後端伺服器、資料庫或需保管密鑰的第三方服務。
  • 擷取器不得接受任意 URL（REQ-S-001）。
  • 所有 GitHub Actions 第三方 action 必須鎖定完整 commit SHA（REQ-S-005）。
  • GitHub Pages 無法自訂完整 HTTP response headers——CSP 只能用 <meta>，非 response header（REQ-S-007）。

§4 外部介面需求

4.1 使用者介面

單頁 React 應用，主要區塊：KPI 摘要、來源／查詢模式／新鮮度狀態列、篩選列（機關下拉、日期範圍下拉、案名／案號搜尋框、招標方式下拉）、標案列表、資料來源說明可展開面板。無障礙需通過 axe-core serious／critical 零違規；響應式需在桌機 1440×1000 與行動 390×844 皆不得水平溢位。

4.2 對外部系統的介面（唯一外部依賴：PCC）

介面 方向 說明
PCC 標案查詢頁 HTML 讀取 固定 origin/path，dateType=isNow（例行）或 isDate（首次回填），逐頁跟隨「下一頁」連結
PCC 標案詳情連結 使用者點擊導出 link 欄位限定 PCC HTTPS scheme／host，rel="noopener noreferrer"

系統沒有對外提供任何 API（無 /api/* 端點）——前端僅讀取同源靜態 JSON（REQ-F-004）。

4.3／4.4 軟體與通訊介面

public/data/tenders.json 是前端與資料擷取管線之間唯一的資料交換介面。全站僅 HTTPS，CSP 透過 <meta http-equiv> 落實，禁止 inline script、unsafe-eval、外部來源。

§5 資料設計

  • 去重鍵：id／announcedDate／link 組合，新資料覆蓋舊資料。
  • 滾動視窗：以 Taipei 日曆日計算，剪枝 announcedDate 早於（今日 − 30 天）的記錄。
  • 機關欄位：org 限定 ORG_LABELS 列舉值，比對優先序固定（中央機關 > 直轄市 > 縣市政府 > 國營事業）；非白名單機關靜默排除，不計入拒絕率。
  • Schema 版本容錯：先 peek schemaVersion，不相符視為「無可用基準」而非拋錯，避免新舊 schema 交接死結。

§7 錯誤處理與 Fail-closed 策略

設計原則：任何非預期狀態一律 fail closed（非零退出、不發布），已知的合法邊界情況（PCC 確認零筆標記、跨日不比較）明確排除在 fail-closed 條件之外，避免誤將正常情況判定為異常。前端只需處理「舊資料 vs 完全無資料」兩種降級，不需自行判斷資料正確性。

§8 安全設計

完整資產／威脅／控制對應見 threat-model.md。設計層面關鍵原則：最小權限（只有 deploy job 有 Pages／OIDC 寫入權限）、輸入不信任（PCC HTML 全程視為不受信任）、供應鏈把關（Action 鎖 SHA、CodeQL、Dependency Review、npm audit）、CSP 僅 <meta>（GitHub Pages 平台限制）。

§3 測試策略

採 TDD（測試先行）：每項需求先以 failing test 證明缺少行為，再實作最小修改，最後重構重跑。

§3.3 風險導向測試優先序

高風險 中風險 低風險
風險 領域 理由 對應層級
高 資料完整性（parser、contract、hash、滾動視窗合併） 錯誤會直接污染公開發布的資料，且不易被使用者發現 Unit + Parser fixture + Contract
高 資安邊界（SSRF 防護、CSP、Action 權限、秘密外洩） 一旦失守影響範圍超出本專案 Security 全系列
中 前端篩選／排序邏輯 影響使用體驗但有 fail-closed 資料層做後盾 Component + E2E
中 Workflow job 相依與 timeout 設定 設定錯誤導致發布失敗，但不會發布錯誤資料 Security(workflow) + 人工驗證
低 版面／樣式細節 不影響資料正確性與安全邊界 E2E 視覺快照人工檢視

§5 退出準則（Exit Criteria）

一項變更視為測試完成，需同時滿足：

  • validate:code（format／lint／typecheck／test:coverage）全部通過。
  • Coverage 達門檻：Statements/Lines ≥ 90%、Branches ≥ 85%、Functions ≥ 90%，parser lines ≥ 95%。
  • security:repo／security:workflows／workflow:lint／security:dist 全部通過。
  • build 成功且 validate:html 通過。
  • test:e2e（8 案例）全部通過，axe serious／critical 為零。
  • security:history（Gitleaks 全歷史掃描）零發現。
  • npm audit --audit-level=high 零筆 High／Critical。
  • 涉及資料擷取邏輯變更時，額外要求一次 workflow_dispatch 手動觸發驗證。
任何一項未通過，該次變更不得視為完成（對應專案鐵律「驗證後才能說完成」）。

§8 缺陷管理

本專案規模尚未使用獨立缺陷追蹤系統；缺陷等同於 failing test 或 CI 紅燈，修復流程比照 §3 TDD 策略（先重現為 failing test，再修復，再重跑全部退出準則）。歷史重大缺陷案例記錄於 ADR-002 與 ADR-001 附錄。
